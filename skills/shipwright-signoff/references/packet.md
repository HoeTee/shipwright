# Human review packet

人工审核是 AI 已完成修复、验证与复审后，PR 合并前的最终检查。展示位置可以是当前对话、网页或 Git 平台，结论始终绑定同一 PR 和确切版本。

人核对最终行为、关键代码、实际证据、剩余风险及是否同意合并。范围内可确认的技术问题由 AI 阶段处理，不逐条提交修复许可。人工要求修改时返回 AI 阶段，沿用原审查计数；新版本完成相关验证后，再请人核对受影响部分。

## Principles

先给人一页能判断的材料，再按其需要展开。审核对象是行为变化、关键逻辑及风险；不要把完整脚本或一串绿色检查作为唯一材料。始终保留完整 diff 与源码入口，片段不能隐藏重要条件或调用影响。

按 [progress interaction](../../../references/progress-interaction.md)更新同一任务入口。进入人审时首屏突出具体待决定项、推荐、影响和关键片段；聊天同步该问题，证据供展开查看。没有正式待决定项时不把普通交付标成“等待批准”。

这是把原文“为需要理解的代码局部生成 explainer”落实为审核材料的做法，不是声称原文规定了固定模板。
来源：[Sharing context across the team](https://claude.dev/blog/solving-code-review-at-anthropic/)。

## Writing

准备审核包时，按 shipwright-write 选择读者、结构与产物语言，再按 shipwright-write 检查含糊结论。中文、英语和其他目标语言共用证据要求，具体句法按目标语言处理。

用户临时问“这个项目怎样工作”或“为什么这样设计”时，分别使用 shipwright-how 和 shipwright-why。只读取相关源码与方法，不因此启动整条执行流程。使用本 skill 的呈现要求仍由主入口决定。

## Choosing excerpts

1. 从 PR 目标和实际 diff 识别行为变化点，优先副作用、权限、状态、数据、边界、错误处理及配置消费。
2. 片段给出文件、已核实的行号及对应 commit。需要时显示前后版本。
3. 为理解保留入口、调用方、被调逻辑、前置条件与输出消费方，片段长度按因果链决定，不机械限行数。
4. 纯重排不与关键业务修改争夺注意力；提供可查入口即可。高影响修改展开更充分证据。
5. 人看不懂时换用该仓库真实代码继续解释，不让其自己复制文件，也不改用无关发明例子。

## Explainer questions

- 这段原来做什么，现在改变什么，为什么需要改。
- 谁调用它，哪些输入来自用户、配置、状态或上游字段。
- 内部关键条件如何选择分支，哪些函数真实执行。
- 输出、状态与副作用传给谁；跨脚本、进程或 API 的交接是什么。
- 失败、取消、超时或异常如何传播；该变更怎样影响调用方和最终产物。
- 哪些结论有执行证据，哪些仅静态推断，尚缺什么验证。
- 现有检查能拦住什么、会漏什么，需要人判断什么。

按用户理解程度解释必要术语。简单改动用短文与片段，复杂关系按需增加调用图或数据流图。解释必须来自当前代码和配置，并附源码入口。聊天正文与 HTML 均按主入口要求提供；图是可选辅助，不能因此省略报告页面。用户明确要求其他呈现、缺少运行环境或渲染失败时，按主入口说明实际情况并给出聊天结果。

## Severity

人工审核报告必须包含 P0/P1/P2 分级摘要和逐项发现。首轮、复审及最终人审沿用同一标准；项目已有严重性标准时保留原级别，并说明与下表的映射，不能借转换降低项目门槛。

| 级别 | 含义 | 示例 |
|---|---|---|
| P0 · 紧急 | 在支持的正常使用路径中普遍导致灾难性后果，必须立即处理 | 启动即无条件删除用户数据 |
| P1 · 高 | 可达路径会破坏核心功能、权限或数据安全，应优先修复 | 普通用户能读取其他用户的私有记录 |
| P2 · 中 | 有明确触发条件和实际影响，范围较小，仍需修复 | 已承诺支持的空列表输入导致该操作失败 |

按实际影响和触发条件分级，不凭改动行数、审查者数量或猜想升级。风格偏好和无实际缺陷的精简建议另列“非阻断建议”，不为填表制造 P2。未证实的疑点单列所缺证据，不计入已确认发现。

报告按 P0 → P1 → P2 排序，开头分别列未解决数量。已修复、已接受的剩余风险及误报单独记录，保留原发现编号和级别，避免混入当前未解决计数。零发现也写 `P0: 0 · P1: 0 · P2: 0`。

每项包含：`[P1] 简明标题`、文件/行号/commit、触发条件、实际后果、证据与执行状态、建议修复、处理状态及是否阻断。严重性和合并门槛分开记录：P0/P1 默认阻断，P2 是否阻断依项目规则及已确认处理决定；明确的必修要求不能因标为 P2 而跳过。没有项目决定时保留未解决状态和推荐，不自行接受风险。

正例：`未解决 P0: 0 · P1: 1 · P2: 0`，随后展示 `[P1] 下载接口缺少记录归属校验` 的触发、证据和阻断状态，已修复发现另列。
反例：只写“已发现两处问题”，把已修复问题计为未解决，或因 CI 全绿而隐藏未处理的 P1。

## Default packet

| 内容 | 要求 |
|---|---|
| 对象 | PR 链接、源 commit、目标分支及 CI 对应版本 |
| 目标与范围 | 原问题、预期、修改前后行为、相关路径和不确定项 |
| 分级发现 | P0/P1/P2 未解决数量与排序后的逐项记录；分开列已修复、剩余风险、疑点及非阻断建议 |
| 关键片段与 explainer | 按上述规则解释实际因果链；附完整 diff |
| 技术证据 | 本地和 CI 的实际命令/结果，AI 发现与处理，已验证/未验证范围 |
| 业务结果 | 可打开或查看的实际产物、关键场景结果及剩余风险 |
| 用户决定 | 列出需要业务或架构取舍的具体问题，给建议及理由；请求通过、修改或暂缓 |

资料不足先补证据，不能把未知正确性交给非技术用户盲目签字。Explainer 不是测试或独立审查的替代品。不要用只挑成功路径、遗漏关键信息的说明包装改动。

## Record

默认在当前对话展示材料，用户也可直接在平台审核。记录 PR、commit、用户原话结论、证据及未解决项，不把沉默或“看到了”当作通过。用户只同意方案，不等于已验收实现。

有授权时把结论与来源记录到 PR；由 Agent 代记时标明“用户结论代记”，不能伪装用户账户的 review。不能写平台时保留绑定版本的本地记录，明确远端尚未记录。

聊天验收首先约束 Agent 流程，不自动等于平台原生 Approve。按平台实际权限和既有规则满足合并门槛；例如 GitHub PR 作者不能批准自己的 PR。不得用机器人审批冒充第二个人，或为了通过而绕过已有保护。
[GitHub 审批说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)。

新提交、基线或配置变化影响已审核结论时，重新验证并请人核对受影响部分；保留仍成立的证据，按平台规则处理旧审批。通过后在已有授权内进入合并或交付合并，不擅自扩大为发布、部署或恢复授权。
