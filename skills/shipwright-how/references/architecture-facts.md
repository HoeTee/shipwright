# Explain the implementation from the current code

适用于项目介绍、调用链、字段传递、职责与函数行为问题。保持本次提问范围，不自动启动审查执行。

## Input and output

输入为用户问题、仓库位置和相关版本。输出为问题的直接答案、真实入口与调用链、输入输出、关键条件、最终消费方，以及可核对的文件位置。无法从现有代码确定的部分明确说不确定。

## Steps

1. 先读项目入口与已有索引，定位用户实际操作涉及的模块。
2. 从入口跟踪输入来源、分支、状态变化、返回值和副作用；解释函数时明确输入和输出。
3. 跨 API、进程或脚本时，核对两端字段、数据归属和失败传播。不要只列函数名。
4. 以用户可观察的行为组织答案，附当前文件与行号。设计动机交由设计依据方法查证。
5. 已有有效上下文继续使用。只有需要新的行为证据时，才在授权范围内运行相关入口。

## Architecture facts for a rules draft

生成 `CLAUDE.md` 或 `REVIEW.md` 草案时，在上述调用链基础上补齐下表。只整理与当前审查相关的现有结构，不启动设计、实现或多方案比选。

| Element | Check |
|---|---|
| 模块与职责 | 实际入口、模块承担的任务及其调用方；附源码或资料位置 |
| 接口与数据交接 | 生产者、消费者、真实字段或签名，以及正常和失败返回 |
| 状态归属 | 谁创建、读取、修改和清理状态；跨进程或并发时是否共享 |
| 约束与未知项 | 已确认的兼容性或权限要求；缺少依据的设计理由交由设计依据方法查证 |

没有代码或资料支持的结构标为待确认，不编造目录、接口或已验证结果。输出交给规则起草步骤，不自动写入项目文件。

正例：从路由和 Worker 核对任务字段、消费入口及状态写入者，再写入规则草案。
反例：看到队列依赖就断言项目已实现任务隔离，或因缺少说明文件而重新设计架构。

## Checks and boundaries

正例：解释上传请求怎样创建任务、谁消费任务以及结果怎样返回，并指向实际代码。
反例：仅依据模块名字编故事，或把静态推断写成已经运行通过。

回到提问给出答案；属于执行阶段的调查则交回证据，继续原阶段。
