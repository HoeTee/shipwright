计数和上限只定义在 [shipwright-fix](../SKILL.md)。本文件不另写数字，也不另定从哪一次起算。开 PR 前的执行和修改是 Pre-PR iterations，不是 AI 审查。CI 重跑、网络重试、同一版本的重复事件和人工评论都不加一。

## AI phase

AI 阶段连续完成审查 → 修复 → 验证 → 复审，无需逐条或逐轮请求人工批准。主 Agent 核实并修复本次范围内的问题；独立审查角色只读固定版本，修复后再审新版本。必需检查通过且阻断项清除后，才请求人工最终检查。

修复前核对工作树、任务分支及内容是否对应固定的受审版本。审 PR 时，若当前 HEAD、分支或额外改动不匹配，从已固定的 PR head 准备隔离工作树或候选副本，不直接在另一分支返修，也不切换、重置或覆盖用户原工作区。本地未提交候选先记录纳入范围的暂存、未暂存及新文件快照，只修改本次范围，保留无关改动。候选已变化时重新核对版本与差异；修复后的验证和复审绑定新候选。

无法依据现有契约决定的需求取舍、超出任务的修改或缺少操作权限，单列具体问题，不自行扩大范围。提交、推送、平台评论和合并仍须有相应授权；默认本地修复不等于允许这些操作。缺少远端写入授权时，交付本地修复与证据并标明远端状态，不把旧 PR 的检查当作新版本证据。

正例：发现解析函数的边界错误后，主 Agent 修复根因、运行相关检查并交独立复审，通过后一次提交最终人审材料。
正例：当前工作区在分支 B 且有用户未提交内容，待审对象是 PR A；从 A 的固定 head 准备隔离工作树返修，B 的原有内容保持原样。
反例：每发现一处可确认缺陷就等待人批准修复，或一边独立审查一边修改同一受审快照。

## Before the PR

明确复现、已确认或待确认根因、预期、范围、影响和验收。执行 shipwright-test，保持变更聚焦。使用环境允许的独立审查入口检查变更及相关调用链，处理有证据的问题。已有项目的修改前后提交约定继续遵守。

本次范围内返修按 [最小完整返修](#最小完整返修) 核对共享根因、相关入口及必需验证。

只读或仅提方案的任务不创建修改。新增业务方向或架构取舍先交用户判断，必要问题在此解决，不等最终人工关口。

## Minimal complete fix

完整流程中的本地修复，或另行获准的返修，使用本节；明确只读时只给建议。先查共享根因及相关调用方，再选择能完整解决问题的最小修改。

- 优先复用仓库已有实现；其次考虑标准库或平台能力、已有依赖。遵守现有组件与接口约定，不为几行代码引入新依赖。
- 核对本次影响的调用方、测试、夹具、配置、导出及资源入口，一次补齐相关修改。无实际需要时不增加抽象、包装、选项或未来扩展。
- 移动、合并或删除代码时保留必要的校验、错误处理、安全和可访问性要求。差异更短不能成为漏修或降低验证的理由。
- 对新增或变更的风险逻辑，补能观察行为错误的针对性检查，并执行项目既定必需验证。一个小测试不是既有检查的上限；低影响文字不机械加单元测试。
- 如确需保留局限，记录具体限制及重新检查条件。注释不等于获得安全或数据约束的豁免。

正例：错误源于共享解析函数，修复该函数并核对调用方及相关检查。
反例：分别在多个调用方加补丁而遗漏共享根因，或为减小 diff 删除错误处理和失败断言。

## AI review requirements

首次执行审查或复审时按需读取 [adversarial review](../../shipwright-review/references/adversarial.md)。共享接口、状态、配置或产物消费发生变化时，结合 shipwright-impact 检查 diff 外的实际消费者。方法的结果回到本节的意见处理与轮次规则，不另建返修循环。

首次读完整 diff，并核对 PR 意图、相关契约、调用关系、正常及失败路径。读取项目约定和 REVIEW.md，按变更风险选择深度；有实际敏感边界时补专项安全审查。

每项发现按 [severity](../../shipwright-signoff/references/packet.md) 报告 P0/P1/P2、是否阻断、文件/行号/commit、触发条件、实际后果、依据与建议验证、处理状态。先汇总各级未解决数量，再按级别排序，已处理项另列。区分新增问题、受改动激活的旧问题、无关存量问题、待验证疑点和误报。没有需修复项时直说，不为凑数量制造评论。

作者先核实意见，再修复或附依据处理误报。风格交给已有工具，避免无价值改写。同类缺陷检查本次影响范围内的其他实例，复用原线程；无新证据不重复报告已处理事项。

复审围绕新增 diff、原发现是否解决和关联影响，保留必要上下文。范围或核心方案变化时重新评估完整影响，不因“只看 diff”漏掉调用方。

## Automatic round cap

计数和上限只在 [shipwright-fix](../SKILL.md)。开 PR 前的执行和修改记入 Pre-PR iterations，不算 AI 审查。开 PR 之后每次 AI 审查加一，不清零。换方法、恢复会话、重开同一任务的 PR，都不重置。

正例：开 PR 前改过两次，Pre-PR iterations 是 2，AI reviews since PR 从 0 起算。反例：把开 PR 前的次数算进 AI 审查，或用开 PR、换方法、重开 PR 把计数清零。

无阻断项就结束循环，不必凑满。到上限仍有阻断项，就停止自动返修，做一次有界复盘：为何没收敛，已试过什么，替代做法、影响和验证计划。必要时建议收缩或重做，不默认推翻整个项目。然后交付未解决项、证据、复盘结论和明确推荐。复盘本身不计新的审查，也不授权再审一次。额外执行要有新的计划和明确授权，原计数保留。

这是失败后的方案决策，和技术通过后的最终人工审核分开。正例：发现多次遗漏迁移入口，先核对全部消费方并给出验证方案，再就超出上限的尝试请求决定。反例：同一做法再补一行就称为换方向，或把同意继续修复当作批准最终合并。

不能自动关闭 PR、放行、拆出相同任务重置计数或无限加补丁。需求冲突、重大取舍或超出授权立刻交给用户，不必等到上限。口头改这次的上限是唯一的临时覆盖，由 shipwright-fix 的脚本写进分母。不要把数字写进 `AGENTS.md`。

## Repeated fixes on one premise

两个或更多修复基于同一前提，且仍未通过同一检查时，在下一次修改前写明并直接验证这个前提。用能区分前提真假的观测定位原因；前提被否定就调整根因判断，前提成立则继续追查未解决原因。记录尝试、观测及结论，不凭再次加大参数继续修补。

例如，两次增加超时时间仍未得到结果，先核对任务是否真正启动、由谁消费、卡在哪一步。检查前提不增加审查额度。已经到上限就只做有界复盘并报告，不能借调查再开一轮返修。
