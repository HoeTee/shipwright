# Test layers

实现或修复前读本节。已有项目矩阵先复用，再更新受影响部分。分层以本文为主。回归不是单独一层，它指防止旧行为被破坏，可以落在任何一层。

shipwright-test 定规则。build 写测试并执行，ship 把同一命令放进 CI。端到端由 shipwright-verify-create 生成的 `verify-<app>` 执行。形式化归 shipwright-prove-create 和 shipwright-prove-maintain。性能数字归 shipwright-perf。UAT 归 shipwright-signoff 和 shipwright-deploy。构建与部署适配归 shipwright-deploy。

「这次真实验收要跑几个任务？」由 shipwright-signoff 问。本文保留真实任务的证据字段和通过标准：入口存在、帮助命令、健康响应或预置成功文件都不够。

只有单元测试不算验证完成。影响交互的改动还要实际操作并按 [evidence.md](evidence.md) 留证。涉及性能还要有前后数字。

## Design map

| 层 | 查什么 | 何时、谁来跑 |
| --- | --- | --- |
| Lint 和类型检查 | 未定义变量、类型错误、项目约定；用项目实际在用的工具 | 每次改动；本地和 CI 同一命令。test 定规则，build 跑，ship 进 CI |
| 单元 | 一条业务规则的正常、错误、边界 | 写代码时。bug 先写失败用例（见 [tdd.md](tdd.md)）。build 执行 |
| 特征测试（钉住行为） | 重构前记下现有行为 | 动结构之前。build 的重构剧本 |
| 接口 / 契约 | 对外承诺的输入、响应、错误、权限、副作用，不能只看 200 | 写代码时补，CI 跑 |
| 集成 | 几个真实组件拼起来的字段、状态、失败传播 | 写代码时补，CI 跑 |
| 端到端 | 像用户一样走完一条重要旅程，按证据规则留截图 | 提交前、PR 中、发布后。`verify-<app>` 执行 |
| 视觉一致 | 迁移前后图像差异为零 | 改样式或迁移组件时。见 [visual.md](visual.md) |
| 性能 | 前后各跑多次取中位数，找出限制因素 | 改热路径时。shipwright-perf |
| 形式化 | 并发、状态机在所有情况下都成立 | 代价最高的模块。prove-create / prove-maintain |
| UAT（用户验收） | 用户确认这就是要的 | 合并前人审；发布后目标环境。signoff、deploy |
| 构建与部署适配 | 产物、启动、配置在目标环境能用 | 改运行方式或发布时。deploy |

```python
# 单元：一个函数对不对
def test_calc_price():
    assert calc_price(100, 0.9) == 90

# 接口 / 契约：对外承诺的行为，包括权限和错误
def test_other_user_cannot_download(client, token_b):
    r = client.get("/orders/42/download", headers={"Authorization": token_b})
    assert r.status_code == 403

# 集成：真连数据库，看写进去能不能原样读回来
def test_order_roundtrip(sqlite_db):
    order = Order(id=1, amount=900)
    save_order(sqlite_db, order)
    assert load_order(sqlite_db, 1) == order

# 端到端：像用户一样操作（verify-<app> 里写的就是这类步骤），并按规则留截图
def test_checkout(page):
    page.goto("http://127.0.0.1:8000")
    page.click("text=下单")
    expect(page.locator("text=订单已提交")).to_be_visible()
    save_evidence(page, "<plan-id>", "<candidate-sha>", "after", "checkout-submitted")
```

`save_evidence` 的路径和命名见 [evidence.md](evidence.md)。

## Source rules

下面是从行为契约生成本地验证与 CI 的全文。链接已改到 shipwright 的 skill。审计测试质量时同时读 [coverage.md](coverage.md)。

## Reuse and upkeep

先找仓库已有的验证命令、脚本、项目验证 skill 与功能地图，核对是否对应当前代码。已有有效入口直接使用。需要建立可重复的真实操作入口时，读取 [shipwright-verify-create](../../shipwright-verify-create/SKILL.md)；入口、前提或配方失效时读取 [shipwright-verify-maintain](../../shipwright-verify-maintain/SKILL.md)。没有修改授权时只登记缺项，不擅自生成或修复文件。

建立一次验证入口、一次变更的受影响验证、完整维护全部登记功能，是三个不同范围。分别记录覆盖和剩余缺口，不用单个功能的实跑证明整套业务已验收。

## Derivation order

对每条关键用户行为或模块规则填清：对象及真实执行边界 → 必须成立的条件 → 失效影响 → 验证方法 → 运行位置和依赖 → 命令 → 通过条件与失败处理。

先看现有测试实际断言及替换了什么，再登记复用。测试文件数量、覆盖率、函数名或没有抛异常，不证明业务正确。预期结果来自已确认契约，不能仅复制当前实现输出。

| 验证 | 选择办法 |
|---|---|
| Lint | 使用项目实际工具和版本，处理未定义变量、可静态判断的错误与约定 |
| 类型检查 | 按语言及项目采用真实类型工具，说明范围与存量基线；语法编译不能替代类型检查 |
| 单元 | 验证独立业务规则的正常、错误与边界行为；允许调用内部辅助函数，不要求每个函数各有专属测试 |
| 接口 | 为对外承诺支持的 API 建契约清单，覆盖输入、响应、错误、权限、状态和副作用；不能只看 200 |
| 集成 | 按真实组件交接检查字段、状态、归属及失败传播，明确哪些依赖是真实的、哪些被替换 |
| 端到端 | 选择重要完整用户旅程，核对最终行为和产物，不枚举函数组合 |
| UAT | 人核对实际业务可接受性及真实消费方式，不用一组自动测试冒充用户验收 |
| 构建与部署适配 | 检查目标产物、启动、配置消费、依赖与目标约束，必要时读部署参考 |

单接口描述被测对象，集成描述参与范围，两者可以重叠。unittest 是运行器名称，不说明其中所有用例都是单元测试。回归描述防止旧行为被破坏，可覆盖多个层级。不要为名称互斥而重复测试或搬动整个目录。

## Choose the check scope

1. 关键新增或变更规则检查正常行为、相关错误分支与边界。
2. 修复能复现的缺陷时保留修复前失败、修复后通过的样例；不能复现时标明限制和复验步骤。
3. 共享接口、状态、配置或数据变化，沿调用关系补相关使用方与失败路径。
4. 纯转发和低影响文字不机械增加单元测试；已确定的项目检查仍执行。
5. 已登记的快速稳定回归按项目策略持续运行。昂贵、真实依赖和人工检查由明确触发条件决定。
6. 并发用例从实际槽位、排队和隔离契约推导；时限先说明依据并校准，不复制某项目的请求数或秒数。

返修前明确哪些检查输入改变、哪些旧证据仍有效，按 [执行效率与迁移核查](../../../references/execution-efficiency.md)选择重跑范围。重命名/迁移同时核对导入、进程、测试发现、CI、构建和当前文档命令；实际执行数量为零不能证明回归通过。

正例：文档命令修复实际运行该命令，确认非零断言并保留原产物输入未变的运行记录。反例：链接测试通过就认定代码块内的命令也正确，或每次小改都无理由重跑全部昂贵验证。

## Repeated defect classes

审查记录或已确认修复表明同一类错误至少出现两次时，核对现有检查为何没有拦住。只读审查给出证据与修复建议；已有返修授权时，在本次范围内优先消除共享根因，或补合适的类型、lint 或行为回归检查。选择最小有效办法，不自动扩大为架构重写。

让检查在真实的旧错误或等价坏输入上失败、修复后通过，复用既有验证入口；适合 CI 的稳定检查接入同一清单。仅增加文字提醒不算防止复发，检查仍不能证明的部分要保留限制。项目既定必需检查照常满足。

正例：不同接口重复漏掉归属校验，修复共享授权入口并用无权限用户访问他人记录的用例验证拒绝结果。反例：只在文档增加“注意权限”，或增加一条错误实现也能通过的测试。

## Critical business tasks

完整试跑可运行产品，或变更影响关键用户旅程、执行器、模型与提示词、状态或交付产物时，先登记完整业务任务。已有项目规则直接复用。仅改说明文字或格式时，依据受影响输入决定复用范围。

启动真实业务任务前，先找用户是否已确认本批适用数量。数量明确就沿用。数量未定，只问「这次真实验收要跑几个任务？」等待回答期间可以准备候选环境和执行方案。历史批次大小只用于设计参照。

Agent 根据当前改动、项目约定和相关历史 session，选择已获准的样本、入口、环境、并发方式、预期结果和通过标准。优先复用最近明确批准且有执行证据的案例，再按当前版本和配置调整。批次按用户选定数量执行。数量覆盖不到某条边界时，单列该边界的验证状态，保留原批次大小。

项目或用户要求真实任务时，使用获授权的业务样本和真实执行链路。必须使用真实模型或外部服务的场景也一并登记。在最终人工合并审核前记录真实任务证据；仅项目事先明确定义为发布后现场验收的目标专属检查保留到对应阶段。该检查标为“发布后待验收”，注明依据、责任和执行办法，不标通过或替代合并前必需检查。不可达本身不构成延后理由，缺项须标明影响并继续核对独立证据。离线 CI 保持原有验证职责。

正例：项目已规定发布后核对生产回调，合并前完成必需测试，报告单列回调待验收及责任人。反例：合并前必需的真实任务无法执行，就临时改称发布后检查并请求放行。

证据至少包含候选版本及实际运行版本或产物、环境、样本标识、任务编号、实际执行组件、终态及业务产物断言。入口存在、帮助命令、健康响应、预置成功状态或只下载占位文件均不足以通过。复用旧证据时核对该任务曾真实通过、相关运行输入及环境契约相同，并记录等价依据和执行时间。

正例：合同审查项目只问用户本次跑几个。用户选定数量后，Agent 参考该项目之前的验收 session，确定获授权样本和并发方式。通过 API、队列、Worker 和真实模型完成审查，再核对审查要点及 DOCX 批注。
反例：用 CI 通过和一份没有审查记录的 DOCX 请求最终人工批准。

## Matrix and execution

| 字段 | 必填内容 |
|---|---|
| 对象、来源与边界 | 对应行为、接口或交接点；真实组件与替身 |
| 正常、边界与失败预期 | 观察什么值、状态、副作用或产物 |
| 入口 | 实际命令、工作目录、依赖、版本与必要配置引用 |
| 运行与触发 | 本地、CI、可达服务环境或目标环境；必需、按改动或发布触发 |
| 通过与失败 | 明确断言、证据位置、是否阻断、由谁处理 |
| 状态 | 已存在、待建立、已运行通过、失败、未运行或不可达 |

每项都落到明确命令和通过条件，不能只写“按需测试”。新工具先配置并实际验证，不把尚未存在的检查当成合并门槛。依赖按项目清单、锁文件与当前系统准备；不把 Ruff、Pyright 等固定给所有语言。

本地与 CI 复用同一清单、配置和兼容版本。CI 可重复相同命令，价值是验证提交到平台的对应版本、记录结果和执行已配置门槛；它不会自动生成用例或发现测试没表达的错误。

## Unreachable external services

- 在调用发送边界检查完整 URL、头、字段、类型、关键内容和失败处理，对照接口说明或已确认样例。
- 模拟响应只能证明程序在给定响应下的处理，不证明服务可达、真实响应或模型效果。
- 能离线核对请求的部分仍应验证，不能因目标在内网而笼统排除接口。
- 目标服务真实链路在可达环境验收。无法执行就保留待验收，不降格为“模拟通过即完成”。
- 专用适配脚本的排除范围由项目明列，不能连带跳过共享模块。

## Evidence and results

记录 commit、命令、环境、依赖、输入/夹具、结果、产物及限制。失败、超时、未运行与通过分别记录。对模型语义使用已标注正负样本并核对结论、引用与最终产物；不把任务完成率当成准确率。

必需检查未通过时继续处理已有授权内的原因，不能靠删断言、跳过任务或改变期望迎合当前输出。无法在当前环境完成时明确缺项与下一步，不交付可合并结论。

CI 的接入和平台操作读 [PR 流程](../../../references/pr-workflow.md)，执行归 shipwright-ship。部署适配的执行归 [shipwright-deploy](../../shipwright-deploy/SKILL.md)。仓库里的部署画像还没有单独文件时，以那个 skill 为准。
