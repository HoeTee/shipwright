# TDD

用户明确要求 TDD、先写失败测试，或在修 bug 之前先写回归测试，并且有一条清楚、便宜的测试路径时，用这一节。

修这类 bug 时，先把坏行为变成可执行的检查，再改产品代码。目标是一条对准这条 bug 的回归测试：修之前失败，修之后通过。

没有便宜路径时不要硬加测试。现有办法需要大套夹具、脆弱的替身、很慢的端到端设施、只有生产环境才有的状态、含糊的复现步骤，或大片无关夹具改动时，跳过新测试，改用最近的有用验证。

## Workflow

1. **弄清 bug。** 写出预期行为、当前行为、受影响路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用这条路径上已经在用的单元、组件、集成或回归测试。看不出实用路径时，不要为了走完流程从零造一条。
3. **先写失败测试。** 加最小的、对准这条 bug 的测试。测试写的是预期行为，不是当前实现的镜像。
4. **先跑这条新测试，再改产品代码。** 确认它因预期的原因失败。它通过了，或因无关原因失败，就先改测试或复现，再动实现。
5. **修 bug。** 用满足预期行为的最小产品改动，并保住旁边的契约。
6. **再跑回归测试。** 确认它现在通过。

## When a failing test is impractical

改用最近的可执行回归检查：对准的脚本、手工复现命令、浏览器自动化、快照比对、日志断言，或范围收窄的集成检查。

宁可没有新测试，也不要一条坏测试。坏测试主要在测替身，写死了实现细节，依赖时序或无关全局状态，为了一处小修去搭昂贵设施，或者证明完修复就该删掉。

## Guardrails

- 不要把测试改成迁就错误的实现。
- 不要放宽已有断言，除非预期行为确实变了，并且理由清楚。
- 回归测试只锁这条 bug。不要大改夹具，也不要顺手扩大无关覆盖。
- bug 不稳定时，尽量把测试做成确定的，并写明锁住的信号是什么。
- bug 暴露的是一整类失败时，先落地这条对准的回归，再考虑同类的其他用例。

## Report

回复里写证据，不要只写结论：

- 写出修之前失败的测试或可执行检查，以及它产生的失败。
- 写出修之后通过的测试运行，以及旁边做过的验证。
- 拿不出修之前的失败证据时，写明原因，并写出用来代替的最近回归检查。
