# Test coverage

目标不是覆盖率百分比，而是哪段没测的代码危险。审计和审查读这一份。发现格式和 P0/P1/P2 用共享的 finding 规则；那份文件由原则组落在 [finding.md](../../../references/finding.md)。给人看时按四段写：这是什么、问题、修法、不修会怎样。

## What to check

- 标出关键路径：钱、身份、数据变更，以及这个仓库存在就是为了做的那件事。看哪些路径是零覆盖，或只有走形式的测试。
- 改动频繁（看 git log）又没有测试的模块，是重构风险最高的地方。标成「先写特征测试」。
- 现有测试的质量：断言没有实际内容；替身太重，测到的是替身；没人读的快照测试；不稳定的写法（真实计时器、真实网络、依赖执行顺序）。
- 缺层：只有单元测试，API 边界没有任何集成；或者反过来，用很慢的端到端去测一个单元测试就能抓住的规则。
- 验证设施：有没有一条命令能知道这套代码能不能用。没有的话，这就是第一条发现，也是任何有风险的改动之前的前提计划。

## How a check earns its place

让检查在真实的旧错误或等价坏输入上失败，修复后通过。复用已有验证入口。适合 CI 的稳定检查接入同一份清单。只加文字提醒不算防止复发。检查仍然证明不了的部分保留限制。项目已经规定的必需检查照常满足。

同一类错误至少出现两次时，核对现有检查为什么没拦住。只读审查给出证据和修复建议。已经有返修授权时，在本次范围内优先补合适的类型、lint 或行为回归，或交给 shipwright-prevent 改结构。选最小的有效办法。
