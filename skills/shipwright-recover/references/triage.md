## Runtime logs

优先读取用户可以导出的材料，可能只有日志。结合实际运行版本、配置引用、失败入口/时间和影响范围定位；不假设最新仓库提交就是运行版本，不要求不可获取的内网访问才能开始调查。

先区分代码、配置、依赖、环境、旧服务未更新等可能原因；每条给已证实事实和待验证推断。缺失信息会改变处置方案时，一次问必要项，例如关键业务是否都失败、是否持续产生错误结果、旧版是否已知可用。不要仅凭报错名称宣布根因。

## Restore or keep the deployment

| 可核对的情况 | 建议 |
|---|---|
| 关键业务持续不可用或影响持续扩大，且有已知可用、兼容的旧版 | 建议恢复运行版并核验可用，同时在开发分支继续修复 |
| 影响局限，其余可用，继续运行不扩大损害 | 可保留当前部署，在开发分支修复，经新 PR 验证后交付 |
| 旧版也有同一问题、数据/配置不兼容，或根因不在当前代码 | 不盲目回滚；处理对应原因，必要时暂停或隔离受影响路径 |
| 运行版、影响或候选旧版情况不清楚 | 明确证据不足，询问最少必要信息；若可能持续扩大影响，先提出限制影响的建议 |

给用户一份可判断建议：事实/推断、影响、推荐选择及理由、候选版本、兼容依据、执行步骤和验证。用户不懂运维时 Agent 仍需提出技术建议，不能只让用户自行决定。

保留当前部署修复，指开发分支修复，不是直接无审查修改运行代码。回滚目标环境不等于错误代码已修复；仓库 revert 也不会自动更新独立部署环境。已写坏的数据需要另行恢复，不能承诺换旧版自动恢复数据。

实际恢复按已确认部署方式及授权执行。内网不可达时由操作者执行并反馈，Agent 不声称恢复完成。日志不足不能自动触发远端恢复或猜测可用旧版。

## Next fix

实际运行问题 → 日志与版本核对 → 根因调查和处置建议 → 开发分支修复 → 本地验证 → 新修复 PR → CI、AI 与人工审核 → 合并与交付 → 目标环境复验原问题。

原 PR 已合并时创建新修复 PR；未合并的返修仍更新原 PR。复用现有项目约定、工具与配置，不重建整套流程。

能复现时先保存失败用例，修复后核对；不能复现则明确依据和待复验步骤，不伪造失败/通过证据。原因只是环境或配置时处理实际原因，不为走 PR 强行改无关代码。

结案依据是用户目标及原问题被对应证据验证解决。仍待用户要求的目标验收时保留等待状态，列出版本、验收步骤及需要反馈的结果；不能把准确登记“待验收”当成已经结案，也不能用外网绿色状态宣称内网根因消失。

## Two learning targets

- 程序回归：用失败输入、响应夹具或业务样本确认行为、状态及产物。
- 代码审查器评测：用已确认的坏改动与干净改动检查真实发现、漏检、误报、重复意见和有害建议。审查器规则、提示词、工具或模型变化时重评。

先选择应由代码、测试、静态规则、项目说明还是审查指令解决。不要每次只往 Markdown 添一句。

按项目需要记录人工投入、AI 审查轮次、有效/误报/重复意见、同类复发、合并后故障和撤销。节省人审时间同时增加排障不算改进。完成率、语义准确性和审查器效果分别报告。
