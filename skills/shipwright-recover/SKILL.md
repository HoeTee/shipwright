# shipwright-recover

何时用：合并之后收到运行日志或故障。
何时不用：正常发布用 shipwright-deploy。回滚不是修复的前置条件。

## Procedure

1. 先读用户能导出的材料。不假设仓库最新提交就是正在运行的版本。不因为内网访问不到就拒绝开始。
2. 按 [triage.md](references/triage.md) 把原因分成已证实的事实和待验证的推断：代码、配置、依赖、环境，或旧服务还没更新。缺的信息会改变处置时，一次问完必要项。
3. 给出可执行的建议，不要只把选择丢回给用户。
   - 关键业务持续不可用，而且有已知可用、兼容的旧版：建议恢复运行版，同时在开发分支修。
   - 影响有限，继续运行不会扩大损害：保留当前部署，在开发分支修。
   - 旧版也有同一问题、数据不兼容，或根因不在当前代码：不要盲目回滚。
   - 运行版或影响还不清楚：写明证据不足。可能还在扩大时，先建议怎么限制影响。
4. 恢复按已确认的部署方式和授权执行。内网不可达时由操作者执行并回传。没有回传就不要写成已经恢复。换旧版不会自动修好已经写坏的数据，仓库 revert 也不会自动更新独立部署。
5. 原 PR 已合并时开新的修复 PR。还没合并的返修仍更新原 PR。能复现就先留下失败用例。不能复现就写明依据和待复验步骤，不编造通过或失败。
6. 同一文件末尾把程序回归和审查器评测分成两类。审查器评测的题和分数归 shipwright-eval，这里只保留这个区分，避免每次只往说明里加一句话。

## Stop

新修复进入 shipwright-build 或 shipwright-fix 时，本 skill 停在建议、授权和证据。结案要有原问题被对应证据验证解决的记录。待验收不能写成已经结案。

## Handoff

新 PR 走 shipwright-ship、shipwright-signoff 和 shipwright-land。目标环境复验原问题后再回到 shipwright-deploy 的验收记录。
