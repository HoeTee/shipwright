# shipwright-teach

何时用：想真正弄懂一块工作，要一份顺着人的节奏讲的大白话。
何时不用：只要运作方式用 [shipwright-how](../shipwright-how/SKILL.md)。只要设计原因用 [shipwright-why](../shipwright-why/SKILL.md)。要写进文档用 shipwright-write。

本 skill 只讲解。不改仓库，不写计划。how 和 why 负责挖，这里负责合成。

## Steps

1. 从对话里判断对方为什么问（准备改、在审查、在排错，还是第一次接触），以及他们已经知道什么。不要考试。已经知道的跳过。深度放在他们的问题上。先定下离开时应该弄懂的少数几件事。
2. 自己只读到能定向为止。然后并行跑 shipwright-how 和 shipwright-why，再合并。子系统两个都跑。小改动可能一个就够。why 默认收窄，把范围写进交给它的问题里（一个收窄的问题，加上 git 和一两个来源），让它按自己的契约记下跳过的来源。只有原因本身才是重点时才放宽。
3. 先用一句大白话下定义：这是什么，有通用名字就用通用名字。再接到眼前的例子（「在 X 里，我们用它来……」）。然后讲它怎么工作、更深的原因、边界情况。讲清它解决的问题和实际怎么发生。对方正在做的那一步能让概念落地时，就顺着那一步走。罗列函数和常量是参考，不是讲解。先给一两句能独立成立的答案，然后停。对方追问再加一层。
4. 这是对话，不是讲课。提议继续或换题，然后跟对方走。不要出题，不要让对方复述，不要宣布「这段很关键」。该停的地方就停，等对方说话。没有人在线时，一次讲完，把「可以再往下」放在结尾。
5. 能打开 diff、代码或调试器就打开。三个以上活动部分不要画在一张图里。每次重画上一张，只加一块，让读者看着系统装起来。从 A 到 B 到 C 就画三次：先 A 到 B，再加 C，再加返回或下一块。流程用 mermaid。空间关系（布局、重叠、滚动、前后对比）在宿主有图像工具时画白板风格的短标注图；没有就用一组 mermaid 或 ASCII。一个简单点不需要图。

完整禁写的套话、句长和目标密度在 [procedure.md](references/procedure.md)。

## Wording

why 的不确定措辞原样留下。那是发现，不是文风。一句一个名字。不写破折号长句，不写镜像句，不写「其余自然成立」这种收束。具体机制用 shipwright-write 的表达规则过一遍。

## Stop

回复就是讲解本身，不要写成工作报告。先给主要的一点，再讲它是什么、怎么运作、为什么，以及还值得用 how 或 why 追的线。不改代码。结果页交给 shipwright-recap。讲解页本身不截图。
