# Numbers

质量在前，硬指标在后。质量没变差，硬指标下降，才算赢。tokens 更少但质量更低，不算赢。

报数字之前，先读共享原则 [explain-the-number](../../../references/principles/explain-the-number.md)（[原则目录](../../../references/principles/README.md)）。评测还要问：每次运行是否真的做了任务，差距是否跨题成立，场景是否就是平时的工作。原则正文不在这里复述。

日常 Run record 里的趋势指标只是信号。没有不装 skill 的那一版，就不能说这次 skill 省了多少行或多少 tokens。

## Metrics

| 类别 | 指标 | 说明 |
| --- | --- | --- |
| 主指标：质量 | 隐藏检查通过率 | 真实修复的测试能不能过；安全题跑恶意输入 |
| 主指标：质量 | 评委评分 | 3–6 条具体标准，只给评委 |
| 主指标：质量 | 完整度 0–3 | 代码更短时，有没有做完整件事。0 是占位，1 缺核心行为，2 缺一条写明的要求，3 是做完了 |
| 主指标：审查类 | 漏检、误报、重复、有害建议 | 来自 lifecycle。只数评论条数不算 |
| 主指标：测试质量 | 需要测试时有没有写；注入小 bug 后测试抓住多少 | 见 [question-bank.md](question-bank.md)。写测试不算冗余 |
| 次要指标 | 改动行数（不含测试）、输出 tokens、用时、费用、对话轮数 | 行数只数源码。测试另行记录 |

判定用 `scripts/stats.py` 的 `decide`。质量显著变差是 `regressed`。质量没有显著变差且硬指标显著下降是 `improved`。差距落在噪声里是 `no-measurable-difference`。说不出限制因素、两组设置不一样、没查出错数，或没确认真做了任务，是 `inconclusive`，并写明缺什么。

## Before you run anything

- 先写下希望能说的那句话，以及什么结果会发布、回退或继续改。问题是用来检验这句话的。
- 读测量脚本。记下它计时、计数和忽略的是什么。
- 看机器是否忙。停不掉别的负载时，各组交替跑，让它们看到同样的噪声，并在报告里说明。

快速估数且用户要的就是一次运行时，一次就够。仍要检查下面的第 4 问和第 7 问，并写明只有一次。在几个选项里做选择时，一次运行不够。

## Seven questions

每问都用来自运行的证据回答。

1. **Why not double?** 点名限制因素。剖析放在不纳入报告的那次运行里，因为剖析会拖慢工作。用进程 CPU、运行时剖析、I/O 等待和系统调用计数，再对到源码。也看负载发生器：它先饱和时，量到的是负载发生器。改动没有移动数字时，先找到限制因素，再称这个改动没有用。评测里的限制因素常常是：题太简单两组都满分、模型能力到顶，或 skill 根本没被读到。
2. **Was it tuned?** 每一侧都按正式用法跑：同一模型、同一推理强度、同样的工具、同样的数据。一侧还停在默认设置时，比的是配置，不是要测的东西。调好再比。调不了就不要从这次运行里挑赢家。
3. **Did it break limits?** 先算账。提升不可能超过 skill 起作用的那部分题的占比。超出这个上限，说明量错了。删掉一段只占运行 10% 的工作，整段最多大约快 11%。超过界限的结果，量到的是别的东西，例如缓存、空操作或 bug。
4. **Did it error?** 数失败和非成功结果，并核对输出是对的，不只是有。拒绝往往很快，超时和重试往往很慢。脚本不数错误时，把计数加上。超时、崩溃、没交付都计入。
5. **Does it reproduce?** 每组至少 5 次，交替跑。报告中位数和范围（最小到最大）。差距小于同组几次之间的波动，就写没有可测差异。接近时用秩和检验或脚本自己的统计。
6. **Does it matter?** 题目要像平时的真实工作，所以从自己的仓库挖。微基准旁边要有用户真正等待的那条路径。一个只占请求 1% 的辅助函数，最多让请求快 1%。
7. **Did it even happen?** 确认工作发生在被计时或被评分的范围里：请求到达了、行写进去了、代码用了结果、实验组读了 skill、对照组没读。懒计算和超时会给从未发生的工作算出数字。

## How to aggregate

同一组的几次结果取中位数。一次偶然特别好或特别差改变不了它。每题先算实验组中位数除以对照组中位数，再对所有题取几何平均，并附 95% 自助法区间。另报「Y 题里有 X 题更好」。区间跨过 1.0，就是没有可测差异。对照组中位数为 0 的题不进比值，在报告里单列。

两组都满分的题太简单。在报告里单列，不拿来证明差异。

`scripts/stats.py` 实现上述算法。`scripts/selftest.py` 在任何一次会花费的运行之前先跑，确认量具本身是好的。

## Report

- 先写判定：`improved`、`regressed`、`no-measurable-difference` 或 `inconclusive`。
- 数字带上单位、次数、范围和限制因素。
- 声称有差异但说不出限制因素、一侧没调好，或第 4 问和第 7 问没查，就写 `inconclusive`，并写出缺什么。
- 计划正文留一个主数字。运行、范围和限制因素放进 HTML 报告。

程序回归（脚本、渲染器坏了）和审查效果（找问题准不准）分开统计，不加成一个分。
