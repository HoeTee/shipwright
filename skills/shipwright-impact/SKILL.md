# shipwright-impact

何时用：改了共享接口、持久数据、配置、状态、并发或交付产物，要知道别处会坏什么。审查里遇到这类边界也用。
何时不用：只想知道调用链用 [shipwright-how](../shipwright-how/SKILL.md)。问当初为什么这样写用 [shipwright-why](../shipwright-why/SKILL.md)。

本 skill 只读，除了为证明那一个前提而写的一次性脚本。那个脚本调用仓库里真实的代码，不改产品代码，不提交。

## Steps

1. 读 diff。看它新增、修改、删除的符号，以及 diff 没写明、但行为已经变了的部分。动机有关时，用 shipwright-why 把 PR 和提交拉出来。
2. 找出「它之所以安全，是因为这一件事」。多数看起来危险的改动，安全与否取决于一个事实。事实成立，一大片风险一起排除。时间花在这里，不花在长长的也许清单上。
3. 搜调用方只是起点。继续看搜索停下来的地方：所调用库的源码、锁死的版本、本地补丁、微任务和卸载时机、API 返回的 JSON、数据库列、线上格式、另一种语言在读同一串字节、功能开关、往下三跳的代码。
4. 每条风险写真实的可能性和真实的代价。确认了的留下。查过并排除的单独列出。引用真实的 `file:line`。搜不到也是答案。不编造调用方或 API。
5. 把那个前提证明到下面能便宜到达的最深一层，并写明停在哪一层。没跑过不能写成已复现。
6. 改动又大又宽时，交给 shipwright-arena，用多个模型问同一个问题，再合并。不把 arena 的流程抄到这里。

五层确定程度、要交回的五段、以及审查时的中文步骤见 [procedure.md](references/procedure.md) 和 [method.md](references/method.md)。

## How sure

1. 你这么说。单独这一层没有价值。
2. 你指出了行。真实的 `file:line`，或库自己的源码。
3. 你走完了失败路径，坏情况到不了。
4. 你跑了。一个脚本或测试调用真实代码，判断错了就会大声失败。
5. 你在运行中的应用里复现了。

第 4 层通常是一个很小的脚本，导入应用实际发布的那个库，调用你担心的那个函数。输出存到 `/tmp/shipwright-<plan-id>/<sha7>/`。新的 head 要新的一次运行。

## Stop

交回：改了什么、那个安全前提及停在第几层、风险、已排除项、合并前最便宜的复现。前提没证明就写 unproven。新产品方向不自动变成返修范围，交回 shipwright-flow。结果页交给 shipwright-recap。
