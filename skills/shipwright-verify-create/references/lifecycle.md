# Project verification capability

用于缺少可重复操作与验证入口的项目。已有有效入口优先复用，不能为了创建方法而重建一套工具。

截图配方只覆盖被验证产品的界面。`answer-me-with-html` 生成的说明页、进度页和审查报告不列入截图或视觉验收，按 [页面检查规则](../../../references/progress-interaction.md) 核对生成结果。证据目录用 `/tmp/shipwright-<plan-id>/<sha7>/`，规则见 shipwright-test 的 [evidence.md](../../shipwright-test/references/evidence.md)。

## Inputs and outputs

输入为当前项目、要验证的用户行为、现有工具、授权和证据位置约定。输出为项目专用验证说明、必要的操作脚本、功能验证地图，以及实际执行证明或明确的未完成状态。

## Survey and design

- 从真实入口确定用户接触的 UI、CLI、API 或其他接口。
- 查现有启动命令、依赖、认证、种子数据、就绪判断和停止方式。
- 优先复用项目的浏览器、终端或接口操作工具。缺项才选择必要工具，不默认安装新测试框架。
- 核对版本与进程归属，明确可隔离的端口、数据和会话。共享实例由一个明确的执行者驱动。
- 证据位置服从仓库约定。业务任务、日志和产物不能随意另存到临时数据根目录。

需要写文件或更改环境时，先满足主流程和项目要求的方案审核。只读任务只交缺项与方案。

## Project verification notes

沿用仓库已有的技能或验证说明位置。写明启动与就绪、只读诊断、用户操作、结果核对、证据保存和清理。命令、选择器、参数与预期均来自本仓库，不留未验证的示例占位。

必要脚本必须有明确调用方式，调用失败可观察。诊断既核对服务可达，也核对版本、认证和关键功能前提。

## Feature map

维护一个索引及按用户功能组织的条目。每项写清前置条件、实际入口、操作配方、预期结果与副作用、证据、失败与不可达原因。

先登记本次必需的关键路径，未覆盖部分明确标注。索引规则、公共操作约定与独立功能分开记录，不能把目录里的每个说明文件都当成业务功能。

## Live run and handoff

先验证一条完整用户路径，核对动作和结果，再检查必要副作用。使用用户要求的真实组件与样本；模拟验证的范围单独说明。不得仅以健康响应或预置成功文件证明业务正确。

失败后清理由本轮创建的进程和临时状态，再处理原因。只停止归属本轮的资源，证据在清理后仍应存在。

交回入口、功能范围、版本、实际命令、产物和缺口。证明操作能力可用，不等于全部业务已验收；本次任务的完整验收继续遵守主流程。

正例：实跑一个登记的用户旅程，并确认最终文件内容与清理后的证据。
反例：只写验证文档就标为可用，或把一条路径成功写成全功能通过。
