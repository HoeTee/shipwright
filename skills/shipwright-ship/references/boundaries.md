## One PR per acceptable change

一个用户目标默认组织为一个可独立验收、合并和恢复的 PR，实施阶段可用多个 commit。大变更若拆分能降低审查风险，先说明各 PR 的独立验收点与依赖，不能仅因目录有数层就机械拆成数个 PR。

用户指定分批、平台限制或确有独立交付边界时沿用。堆叠 PR 保留明确次序，先准备所有必要材料，避免串行重复调查。合并时核对新目标基线和平台门槛，未变的源内容与已成立证据可复用；不能用树相同绕过平台要求的检查。

正例：一次模块重排可以分提交实施，在一个 PR 中审完整落地结果；可独立发布的 API 兼容变更与后续客户端迁移可分 PR。
反例：把同一个不可独立使用的方案按规则层、执行层和接入层各开一份 PR，却没有解释这样拆如何降低风险。
