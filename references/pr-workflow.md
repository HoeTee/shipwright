# PR 审查与复审

启动本流程默认包含本次范围内已确认缺陷的本地修复、验证与复审，包括用户只说「做下 code review」的情况。明确只读、仅报告或仅方案时不修改。先按 [审查对象与规则](review-target.md) 读取规则、锁定基线和受审版本，再查看差异。只加载实际使用的平台资料：[GitHub](platforms/github.md)、[Gitee](platforms/gitee.md) 或 [Git](platforms/git.md)。

## AI 阶段与人工最终检查

AI 阶段连续完成审查 → 修复 → 验证 → 复审，无需逐条或逐轮请求人工批准。主 Agent 核实并修复本次范围内的问题；独立审查角色只读固定版本，修复后再审新版本。必需检查通过且阻断项清除后，才请求人工最终检查。

修复前核对工作树、任务分支及内容是否对应固定的受审版本。审 PR 时，若当前 HEAD、分支或额外改动不匹配，从已固定的 PR head 准备隔离工作树或候选副本，不直接在另一分支返修，也不切换、重置或覆盖用户原工作区。本地未提交候选先记录纳入范围的暂存、未暂存及新文件快照，只修改本次范围，保留无关改动。候选已变化时重新核对版本与差异；修复后的验证和复审绑定新候选。

无法依据现有契约决定的需求取舍、超出任务的修改或缺少操作权限，单列具体问题，不自行扩大范围。提交、推送、平台评论和合并仍须有相应授权；默认本地修复不等于允许这些操作。缺少远端写入授权时，交付本地修复与证据并标明远端状态，不把旧 PR 的检查当作新版本证据。

正例：发现解析函数的边界错误后，主 Agent 修复根因、运行相关检查并交独立复审，通过后一次提交最终人审材料。
正例：当前工作区在分支 B 且有用户未提交内容，待审对象是 PR A；从 A 的固定 head 准备隔离工作树返修，B 的原有内容保持原样。
反例：每发现一处可确认缺陷就等待人批准修复，或一边独立审查一边修改同一受审快照。

## 首轮审查

使用 [独立审查方法](methods/adversarial-review.md) 检查正确性、安全、实际负载、有效测试、性能和必要复杂度，沿用已确定的规则、版本和范围。共享边界变化时结合 [变更影响核对](methods/blast-radius.md)。不要求固定数量或品牌的审查模型。

1. 读完整 diff、PR 意图、相关契约及正常和失败路径。跟随调用方与消费方核对影响。发现敏感边界时加深对应审查。
2. 按风险运行适用的已知检查，或读取已有结果。[验证方法](verification.md) 用于核对范围、状态与证据。
3. 核实每条发现。按 [发现分级](human-review.md#发现分级与排序) 记录 P0/P1/P2、是否阻断、位置、触发条件、实际后果和验证依据。区分新增问题、受改动激活的存量问题、无关存量问题和待验证疑点。
4. 先报各级未解决数量及关键影响，逐项按级别排序，已处理项另列。没有需修复项时直说。风格问题沿用既有自动检查。

## PR、CI 与线程

- 记录 PR、当前 head、目标基线及 CI 的实际验证提交。平台可以测试模拟合并结果，以它和本次 PR 的关联为准。旧版本的绿色结果不能证明新版本已验证。
- 读取必需检查、失败步骤、日志、行内意见和线程状态。线程标为已解决也要核对修复证据。
- 本地候选与远端 PR 不同时，分别列本地检查和远端 CI 的覆盖范围。缺失、跳过、超时或不满足规则的检查保留实际状态。
- 写评论、回记用户结论或推送返修提交只在对应操作已获授权时执行。标明技术意见与实际人工结论的来源。

## 返修后的复审

主 Agent 先核实发现，修复本次范围内确认的问题，或附证据说明不适用，并遵守下节的最小完整返修要求。完整流程沿用已有修复授权；明确只读时只记录建议。查找本次影响范围内的同类问题，并复用原线程。

复审先比较上次受审提交和新提交，再核对原发现、相关调用链和复跑结果。基线或范围变化时回到完整 diff。没有新证据时不重复报告已处理事项。

AI 审查的计数和上限只定义在 shipwright-fix。开 PR 前的执行和修改记入 Pre-PR iterations，不算 AI 审查。开 PR 之后才计数，不清零。无阻断项时结束循环。网络重试、CI 重跑、同版本的重复事件和人工反馈不加一。换方法、恢复会话或重开同一任务的 PR 不重置。到上限仍有阻断项时停止自动返修，做有界复盘，保留原计数。额外一轮需要明确的方案和授权。

## 连续返修仍失败

两个或更多修复基于同一前提，且仍未通过同一检查时，在下一次修改前写明并直接验证这个前提。用能区分前提真假的观测定位原因；前提被否定就调整根因判断，前提成立则继续追查未解决原因。记录尝试、观测及结论，不凭再次加大参数继续修补。

例如，两次增加超时时间仍未得到结果，先核对任务是否真正启动、由谁消费、卡在哪一步。检查前提不增加审查额度。已经到上限就只做有界复盘并报告，不能借调查再开一轮返修。

## 人工审核

必需技术检查和阻断项处理完成后，为当前 PR 与 commit 准备 [人工审核材料](human-review.md)，由人最终核对行为、关键代码、证据与剩余风险。人工检查不承担 AI 阶段的逐项修复审批。通过、要求修改和暂缓均应明确记录；要求修改时回到 AI 阶段，并沿用原轮次上限。缺少必需检查、人工审批或关键证据时列出缺项。提交变化影响结论时，复核相关部分及平台规则。

## 最小完整返修

完整流程中的本地修复，或另行获准的返修，使用本节；明确只读时只给建议。先查共享根因及相关调用方，再选择能完整解决问题的最小修改。

- 优先复用仓库已有实现；其次考虑标准库或平台能力、已有依赖。遵守现有组件与接口约定，不为几行代码引入新依赖。
- 核对本次影响的调用方、测试、夹具、配置、导出及资源入口，一次补齐相关修改。无实际需要时不增加抽象、包装、选项或未来扩展。
- 移动、合并或删除代码时保留必要的校验、错误处理、安全和可访问性要求。差异更短不能成为漏修或降低验证的理由。
- 对新增或变更的风险逻辑，补能观察行为错误的针对性检查，并执行项目既定必需验证。一个小测试不是既有检查的上限；低影响文字不机械加单元测试。
- 如确需保留局限，记录具体限制及重新检查条件。注释不等于获得安全或数据约束的豁免。

正例：错误源于共享解析函数，修复该函数并核对调用方及相关检查。
反例：分别在多个调用方加补丁而遗漏共享根因，或为减小 diff 删除错误处理和失败断言。
