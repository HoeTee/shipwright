Paths are from the shipwright repository root, the directory that contains `scripts/` and `skills/`.
Resolve `scripts/render_html.mjs` and `scripts/render_progress.py` from that root, not from a host-specific skill folder.
The bundled renderer keeps its existing page credit unless the user asks for another line via `--footer`.
Do not screenshot the HTML this renderer produces. Product screenshots follow [evidence](../evidence.md).

# Progress, blockers, and attention

使用本 skill 的实质性答复均采用“聊天核心内容 + 随包 HTML 页面”。首次执行、恢复任务或交付人审时另维护任务进度源；简单问答使用紧凑解释页，不为它虚构任务状态。

## Screenshots and page checks

`answer-me-with-html` 生成的说明页、进度页和审查报告不启动浏览器截图或视觉验收。检查渲染命令退出状态、HTML 文件生成、关键正文、证据、版本和链接目标即可，更新面板后同样检查这些内容。

截图范围按页面用途判断。被验证产品的网页、桌面应用或其他界面可按项目要求截图，即使产品本身使用 HTML。产品截图可以作为证据链接或插图放进报告。建立和维护验证能力时，采用同一范围。

正例：验证产品页面上的权限提示并保存截图，再生成审查报告，检查报告中的文字与证据链接。
反例：把生成的审查报告当成产品页面截图验收，或因报告免截图而跳过实际产品的视觉检查。

## Two outputs on every answer

- 聊天：直接回答用户当前问题，给主要结论、关键依据和必要的限制或待办。解释问题先解释，不机械加入无关 PR、部署或进度字段。
- HTML：统一使用仓库根目录的 scripts/render_html.mjs 生成或更新，附可打开的页面入口；默认紧凑浅色图纸，保留原版 header、字号和表格，隐藏工具栏。短问答也提供页面，用紧凑内容表达，不为凑面板扩写。
- 复用：任务进度更新同一页面与状态源；连续讨论同一主题时优先更新对应解释页，避免一问一份重复报告。阶段结论与最终答复都应包含相应页面入口。
- 范围：普通工具旁白不逐条生成页面；用户明确要求某次纯文本时按该次要求输出，其余答复继续沿用默认规则。

正例：用户追问“tests 与 scripts 是否重复”，聊天直接说明分工及仓库实例，同时用短 HTML 展示对应关系；不因答案短而跳过页面。

反例：只说“已更新，见链接”；或因页面生成 skill 的简短惯例删掉聊天中的主要答案；或只给聊天并称“问题简单，不需要 HTML”。

## Chat and the fixed entry

先识别用户确认的资料根目录和工作区指令，页面、状态与交付资料在该目录下按用途保存。正例：用户要求合并两个资料目录后，后续更新固定链接时沿用唯一目标目录，不根据旧对话重建另一个目录。迁移当前导航和任务指针时保留旧检查时间，原始日志与历史压缩包不冒充迁移后的新执行结果。

任务开始时直接说明本轮范围、接下来做什么、是否需要用户行动。阶段完成、影响后续的阻断、需要决定及结束时主动同步；长任务沿用当前会话的进度沟通频率。普通日志和没有变化的状态不反复通知。

用户不打开网页也应知道现在发生什么。进度消息默认用这五项的简短表达，不强制每次堆五个小标题：阶段、完成/正在做的事、卡点、用户待办、下一步。没有用户待办就明确说“暂时无需操作”，不笼统要求“请审阅所有资料”。

同一任务复用既有页面地址和状态源，不为每轮返修新增报告入口。任务结束保留最后快照；新任务另建任务标识。先回读已有状态与对应版本，再核实当前事实，不把旧快照当作实时状态。

先登记用户的整体目标及完成条件，阶段状态与整体状态分别维护。端到端任务中，本地完成后继续创建 PR，不能宣布 completed 或把 CI/人审转成下一项可选任务。只有用户明确限定本地或只读时，才采用 scoped 目标并保存该范围的用户依据。

正例：本地检查已完成，正在等待平台 CI；暂无需你操作。下一步由 Agent 读取结果并处理失败。

反例：结果见新生成的第七份文档，读完后告诉我怎样继续。

## Core result in the chat

每次答复都让用户不打开网页也能理解主要内容；流程执行中的阶段交付和最终回复还应使用户能判断当前状态。按本次任务选取必要信息，用短段落或少量要点说明：

- 核心结果：实际完成的行为或交付物；涉及 PR 时给出其状态与对应版本。
- 验证结论：实际执行的关键检查及结果；保留跳过、未验证和范围限制。真实业务验收在聊天中列用户确认的任务数、实际提交数和通过数。未确认时只问数量，样本、并发和验收标准由 Agent 根据历史证据准备。
- 剩余卡点：还缺什么、影响哪一步、由谁处理；阶段完成与整体完成分开。
- 用户动作与下一步：现在是否要操作或决定，之后由谁继续。暂无待办时明确说。

随后再给固定进度页、PR 或交付包链接。不要机械堆固定标题；篇幅按复杂度控制。即使 `answer-me-with-html` 建议页面生成后只回两三行，也要保留本流程的核心摘要：压缩文字，不省掉结论、范围与卡点。

正例（说明写法，不是当前执行结果）：PR 已合并，CI 和独立审查通过，交付包已准备；目标环境尚未验收，等待操作者的日志。现在无需再次批准；有结果后 Agent 继续核查。随后附 PR、交付包和固定进度页。

反例：只回“页面已更新，点击查看”，让用户自己从网页里找 PR 是否提交、检查是否通过、是否还要操作。

## Status and responsibility

| Status | When to use it | What the first screen does |
|---|---|---|
| running 正在执行 | Agent/工具确实正在做本轮工作 | 说明具体动作和后续；不制造假实时动画 |
| waiting_user 等待你决定 | 一个必要决定确实阻止对应后续 | 给具体问题、推荐、影响和回复方式 |
| blocked 遇到阻断 | 权限、环境或依赖阻止继续，尚无失败执行结果 | 标原因、受影响步骤、处理者和恢复条件 |
| failed 执行失败 | 有实际失败结果 | 显示失败摘要、影响及谁处理；不要只贴日志 |
| not_started 尚未开始 | 尚未进入本轮或后续阶段 | 不渲染成错误或“等待用户” |
| completed 目标已完成 | 用户要求的全部完成条件已有证据 | 展示最终结果，不能仍有必需阶段待做 |

每个卡点写原因、影响、责任人和下一动作。责任人可以是 Agent、用户、平台或环境操作者，不能默认全部交给用户。存量问题、未来计划与本轮阻断分别标注。

正例：端到端任务已完成本地准备，正在创建 PR；当前无需用户操作。缺少送审范围决定时，明确等待该决定，并继续准备可独立执行的检查。

反例：端到端任务只完成本地准备，就显示“本轮完成、无需操作”，把创建 PR 和 CI 写成建议的新任务。只读任务也不能因尚未部署而被标成执行失败。

## The page and real interaction

首屏按注意力优先级放：用户是否需要行动、当前状态/动作、卡点及责任、下一步、最近结果。显示更新时间与源码/PR 版本。阶段条使用真实状态，不用文件数、测试数计算全流程百分比。

有 PR 时直接列每个 PR 的当前 head、CI、独立 AI、人审和合并状态，不能用“四个 PR 未合并”让人猜是否跑过 CI。缺少记录写“未记录”，不推断通过。CI 与 AI 可并行；最终人审只在必需技术检查通过后提出。

需要用户时，用 action.kind 区分 technical_replan（三轮后的方案决策）、final_review（最终人审）、target_acceptance（现场结果）和 missing_information（缺必要信息）；已有旧状态可不填。用户同意修复不等于允许合并，已通过的合并决定不能被旧渲染脚本恢复为待批准。

正例：首屏显示“CI通过、AI通过、人审待决定、未合并”，并注明这是最终人审。反例：只写“检查通过”，让用户反复追问指测试还是 AI，或人审与三轮异常分流是否同一关口。

详细检查、关键片段、文件清单和历史放入标签页或展开项；重要失败的数量、影响与待决定事项仍在概览可见。人审时先突出需要决定的行为、关键片段和证据，不把用户送进全文件阅读任务。

按钮只提供已经接通的能力。可以查看证据、切换详情或复制指令。没有与会话/执行器连接时，复制按钮明确写“复制给 Agent 的指令”；提示复制成功不代表已提交、已批准或已执行。静态快照说明需刷新查看 Agent 更新，不声称后台自动运行或实时轮询。

需要用户提供尚未知晓的信息时，直接说明提供什么和怎样回复，用 reply_hint 提示；不强制生成带空占位的复制指令。正例：请在当前对话提供已有的私有下载入口或操作手册，Agent 负责其余接入。

正例：点击复制后提示“已复制，请粘贴到当前对话；尚未执行”。

反例：未连接平台的页面放一个“批准合并”按钮，点击后只改本地绿色勾。

## Reusable render entry

每次实质性答复都通过随包 HTML 入口生成；已有页面可更新复用。已有产品界面作为证据或操作入口保留，不自动替代这份回答页面。独立本地进度页使用随包标准库脚本及模板：

```sh
python scripts/render_progress.py /ABSOLUTE/task.progress.json --output /ABSOLUTE/task.html
```

进度页、解释页和方案页都由仓库根目录的 scripts/render_html.mjs 完成排版，无需单独安装 answer-me-with-html skill。解释页直接使用 Markdown 草稿，不强行塞进进度 JSON。只生成 HTML；默认 sheet / blueprint / light，沿用原版 header、字体字号、表格、SVG 与自动布局，只隐藏工具栏。草稿、组件、页首字段和署名写法见 [HTML explainer](html-explainer.md)。需要 Node.js 20 或更新版本；用户明确指定本次其他呈现时沿用其要求。

```sh
node scripts/render_html.mjs render draft.md -o answer.html --no-open
node scripts/render_html.mjs patch answer.html --panel A --from panel.md --no-open
```

状态源可保存选择，后续仍用上面同一条命令更新同一页面：

```json
"presentation": {
  "renderer": "answer-me-with-html",
  "theme": "blueprint",
  "template": "sheet",
  "mode": "light"
}
```

未设置 renderer 时脚本默认使用 `answer-me-with-html`，默认主题为浅色图纸（`blueprint` / `light`）。正例：新任务未指定 presentation 时，页面首次打开即显示浅色图纸；更新旧任务时同步其 presentation，避免旧的卡片配置覆盖新偏好。用户明确要求内置独立模板时可设 `presentation.renderer` 为 `native`；不要为了省事绕开已确认的默认风格。

脚本从既有状态生成简短的 `.view.md`，再调用随包的 scripts/render_html.mjs；既有 presentation.am_cli 仍可指定自定义入口，自定义入口需自行支持所用参数。默认署名为 Generated by、code-review-lifecycle-skill 项目链接、renderer 版本、生成时间和 Star on GitHub 项目链接。--footer 可指定整行纯文本，空字符串隐藏署名；patch 保留上次选择。进度 JSON 可使用 presentation.footer 指定同一选项；省略则保留默认项目署名。渲染不更改任务状态或证据时间。检查按当前事实前置，主页面只列前五项；其中的 command 片段保留代码和说明，人审时将本版本关键片段前置。完整文件、历史与检查仍链接到状态源。工具缺失时准确报缺项，不默默退回用户已否定的外观。

短追问只更新有关说明或紧凑页，不反复重写整套状态与历史。阶段变化从同一状态源渲染一次；普通工具旁白无需渲染。已有工具满足需求时，不为每个阶段另写专用状态脚本。

完成条件的 evidence 可以是文字依据；有可打开入口时另用 evidence_href。旧数据的 evidence 若本身为 http/https/file URL，仍可作为入口。交付证据是文字时显示文字，不强行当作链接；不能因此让整个结果页生成失败。

正例：用户要求沿用 `answer-me-with-html` 后，后续 CI 或验收状态变化仍经该 CLI 更新固定链接，首屏说明阶段、卡点、用户动作与下一步。

反例：为做进度面板换一套自建 CSS，或只修一次 HTML，下次运行原脚本又变回旧外观。

先运行 `--help`，按当前任务事实填写 JSON。格式参考 [progress example](../../assets/progress.example.json)，占位内容不是实际任务结论。脚本只渲染快照，不监听 PR、不连接执行器、不替用户批准。

完成一个关键步骤后更新同一 JSON，再渲染同一页面，并在聊天主动同步关键变化。状态源至少保存整体目标、完成条件、范围、状态、阶段、当前动作、更新时间、版本、用户动作、卡点、下一步及证据。证据带其实际时间，更新页面不刷新旧证据的有效性。

## Check the generated page

用真实任务快照和生成的 HTML 核对当前阶段、卡点、用户待办、下一步、版本及旧证据时间。按上面的截图与页面检查规则验收说明页和报告。被验证产品的交互、窄屏显示和其他视觉要求，按项目要求执行真实点击、浏览器检查与截图。
