# Project setup and rule generation

只在首次建立流程、材料冲突或项目约定需要更新时读取。普通修复复用已有结果。

当前仓库缺少 `CLAUDE.md` 或 `REVIEW.md` 时，按 [Draft rules when they are missing](review-rules.md) 调用内置的实现与架构事实、设计依据、验证、变更影响和技术表达方法。先给缺失文件的完整草案并请用户确认，确认前不写入；只缺一份就补一份，等价规则优先复用。该步骤不自动授权产品修改或 PR 合并。

## 1. Identify the starting point and recover the facts

| Material | What to do |
|---|---|
| 只有想法 | 提炼用户场景、输入输出、目标与非目标、失败反馈、验收标准；提出并标记架构假设 |
| 只有文档 | 标记需求、设计、接口说明或参考用途，复用已完整部分，仅补影响目标的缺口 |
| 已有仓库 | 从入口、清单、核心调用、配置、测试、CI 与交付文档建立当前画像 |
| 仓库加用户文档 | 分列当前实现、已确认要求与本次目标，检查差异和兼容影响 |

先用目录、文件搜索和已有索引定位，再沿相关代码调查。历史对话是线索，不证明缺陷仍存在。用户能提供材料的路径已知时自行读取，不要求其搬运本地内容。

画像回答：用户怎样完成任务；模块及交接契约；状态、数据与外部依赖；语言和实际检查入口；平台、账号与审查能力；开发、CI、构建、发布和部署环境之间的关系。

重要结论记录来源与状态：已证实、推断、待确认、计划。读到测试只说明用例存在；旧记录通过不说明当前版本通过。

## 2. Handle conflicts

- 已实现行为不自动等于正确需求；文档声明不自动等于已经实现。
- 明确目标正确而实现不符：记录缺陷和修复方案，不改需求掩盖错误。
- 实现符合已确认目标而说明过时：更新对应说明。
- 用户提出新目标：说明行为差异、影响与验收。
- 有效要求无法判定：展示具体冲突和推荐取舍，只询问影响业务方向的必要问题。文件日期不能单独决定权威性。
- 新用户指令、既有项目规则与历史建议区分来源，按适用指令优先级处理。

## 3. One-page summary, then the full draft

摘要包含现状、目标、可复用材料、差距、推荐下一步、关键假设和用户需要决定的事项。不要先抛出空技术表格让用户填写。

已有设计满足目标时不重新设计全部系统。只有新增或受影响部分需要展开。规则生成先给完整初稿，按 [Draft rules when they are missing](review-rules.md#ask-with-the-complete-draft) 取得对具体内容的确认后再写入；针对同一草案已有的明确确认直接复用。用户只要求方案或只读检查时不擅自写入仓库。

## 4. How to write CLAUDE.md

以 [CLAUDE template](CLAUDE.template.md)为结构参考，按证据写成实际项目内容：

- 简述目标、非目标、主要输入输出。
- 说明实际模块职责、关键入口与跨模块约定。只有想法时标记“拟议结构”，不编造路径。
- 提炼实现者需要遵守的工作约定与失败行为；详细设计链接权威来源。
- 列出已核实的检查入口、运行前提和触发条件。计划建设的类型检查或 CI 明确标记。
- 摘要说明 Git 平台、人工关口、部署画像与环境边界，链接详细执行资料。

保持入口短。完整需求、日志规范或部署手册已有权威来源时引用，不复制出第二份。适配当前 Agent 实际加载方式，可由 AGENTS.md 等入口引用同一来源。

## 5. How to write REVIEW.md

以 [REVIEW template](REVIEW.template.md)为结构参考，从实际契约与风险推导：

- 重要失败长什么样，哪些后果构成阻断，轻微建议如何限制。
- 模块及关联调用方、必须成立的条件、所需证据、适合的自动验证与人工判断。
- 每条发现给出文件、行号、触发条件、后果与依据；区分新增、既有、疑点与误报。
- 明确排除路径与理由，不按宽泛标签排除共享代码或全部协议检查。
- 定义意见处理、复审、轮次上限及摘要格式。轮次数字只定义在 shipwright-fix，不写进 AGENTS.md，也不写进本文件。没有发现时直接说明，不为填满报告制造意见。

只有想法时先写验收、失效方式与证据标准；模块形成后补路径与具体检查。不是等代码完工才开始，也不是对不存在的实现制造审查结论。

## 6. Project execution notes

可维护一个精简的工作流说明，或复用已有文件，承载：

- 验证矩阵：对象、契约、方法、依赖、实际命令、触发、通过条件与失败处理。
- 平台绑定：实例、仓库、分支、身份、手册、所选工具及已验证能力。
- 人工审核入口、材料与版本绑定；AI 轮次和记录位置。
- 部署画像、交付、目标验收和恢复入口。

不要强制所有项目新增同样数量的文件。每条详细规则有一个权威来源，其他文件引用。

## 7. Deployment confirmation

首次采用某方式或方式变化时读取 [deployment profile](../deployment.md)。Agent 先调查，再给推荐与必要问题，让用户确认目标环境、交付方式和重要取舍。已有明确且未变的决定直接复用。只有想法、部署未定时可暂记待定，不阻塞无关设计。

模板只固定字段和生成要求，不能只替换项目名就复用一个仓库的架构与工具。
